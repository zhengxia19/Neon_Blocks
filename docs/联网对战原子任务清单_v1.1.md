## 0. 强制执行规范

1. 开始一个任务之前：阅读本文件当前任务 + 原方案对应章节 + 指定源码；验证上一个任务已验收。每轮建议只给模型 1 个任务，禁止一次让模型实施整个阶段。
2. 每项必须依次执行 **确认基线 → 小步修改 → 相关单元/集成测试 → 必要静态检查 → 复核边界 → 写证据 → 单独提交**；失败即停止，不得标记完成，不得跳过测试。
3. 原有单机模式必须始终可玩。不要修改 `.github/workflows/deploy.yml`；不引入 React/Vue、视频/WebRTC、D1、KV 或大依赖。
4. 新增协议类型统一在 `shared/protocol.ts`（前后端共享纯类型和校验常量），每个消息都包含版本及类型。`src/game/` 不依赖任何网络或 DOM API。
5. 证据写 `docs/multiplayer-execution-log.md`，每个任务记录：任务编号、提交 SHA、改动文件、实际运行命令与结果、测试用例数量、未解决事项和复审结论。截图及负载数据存 `evidence/multiplayer/`，不写入 API Token、席位令牌或玩家隐私。
6. 对跨多个文件的任务先列出改动清单，原则上限制 **1～3 个逻辑文件 + 最少关联测试**；超过范围应进一步拆分，不允许以全仓重构替代小修。
7. 单机全量回归命令（G0/G3/G4 必跑，其他任务仅按受影响范围运行相关测试）：`npm ci && npm run typecheck && npm run test && npm run build`；E2E：`npx playwright install chromium && npm run test:e2e`。Worker 单测/类型检查按新 package 实际脚本运行。禁止将仅“构建通过”表述为“全部测试通过”。
8. 每个阶段关闭前独立复审：源码与已批准方案逐条比对、检查网络/费用/资源生命周期、检查实测证据与任务状态。无证据任务不得关闭。
9. 生产环境实际发布属于独立的最后阶段，先完成本地模拟/预览验收。Cloudflare 权限和连接已经存在，但**不表示目前创建资源已获授权**；实施时使用已连接工具或经授权的 Wrangler；绝不要求用户在聊天里贴明文令牌。

## 1. 已批准业务规则（所有实现必须遵守）

| 维度 | 固定规则 |
|---|---|
| 房间 | 6 位数字 100000–999999；房主设 2～6 人容量，至少 2 人且全员准备方可开赛 |
| 昵称 | `^[A-Za-z0-9]{1,16}$`；同房间不允许大小写无关的重名；联网中显示昵称 |
| 随机模式 | S1 系统种子全员同序列（默认）、S2 系统主种子按席位派生独立种子、S3 房主自定义 1～32 位字母数字种子全员同序列；全部仍用 7-bag |
| 等级 | 房主选初始 1～10，默认 1；联网 `startLevel + floor(lines/10)`，单机保持 1 起步 |
| 时间 | 服务器权威 600 秒上限；仅剩一名存活时立即胜出；超时存活者按分数→消行，完全并列允许并列 |
| 离线 | 断线宽限 30 秒，期间不延长比赛截止；主动退出算淘汰；全员主动退出立即销毁业务房间；全员意外离线至多 30 分钟回收 |
| 排行榜 | 全房间所有客户端看到**同一份**按得分降序榜单；同分并列名次，消行数→入场顺序仅决定显示顺序；淘汰者保留，获胜者独立标记 |
| 观看 | 总共仅两个棋盘：自己 + 一个观察对象；选择分数刚好比自己高的其他人，否则选择分数最低的其他人；可选已淘汰者的冻结棋盘；绝不因此调整排行榜 |
| 玩法 | 同步竞赛/生存淘汰，无垃圾行、无聊天、无登录、无全球榜 |

### 特别需要在实现前处理的语义

- **玩家人数**：创建房间时指定的是容量而非必须凑满；实际在场且已准备至少 2 人即可开始，开始时锁定本局成员。
- **时间判决**：服务器闹钟到 600 秒时仍有两人以上存活，比较服务端已接受的最新成绩；已淘汰者不能因得分高成为胜者。榜单继续只按得分排序，**与胜负排序分离**。
- **断线/比赛**：服务器仍在计时；客户端暂时中断可视为“断线恢复中”，30 秒未恢复按淘汰处理。避免用后台 rAF 的冻结时间补跑大量帧。
- **排名**：得分并列显示同一名次，服务端生成有稳定 revision 的全员榜单；仅“我”的高亮是本地差异。
- **房间码重用**：使用 `generation` 区分旧业务房间；一旦删除旧数据，旧会话令牌不能进入新占用同一号码的房间。

## 2. 轻量服务器与网络预算（验收红线）

### 2.1 事件驱动拓扑

1. 浏览器独立运行现有 `GameEngine` / Canvas；游戏帧率不受 WebSocket 延迟约束。
2. Worker 仅处理 HTTP 创建/加入/一次性握手票据/健康检查和 WebSocket 升级；具体房间交给 **每房间一个 Durable Object**。
3. DO 使用 **WebSocket Hibernation API** (`state.acceptWebSocket`、`webSocketMessage`、`webSocketClose`、`serializeAttachment`)；**禁止**每房间常驻 `setInterval`、每帧重算棋盘或反复轮询数据库。
4. SQLite 存储只保存**房间配置、席位和令牌摘要、比赛状态、关键时间点、必要的最近成绩与清理截止时间**。远程棋盘最新快照优先保存在内存并在丢失时要求重发，不把每个快照写 SQLite；不得持久化全部历史帧。
5. 定时事件通过 DO Alarms 调度最近到期节点（开局、600 秒结束、断线宽限、空房清理）；一房间同时只有一个有效闹钟时间，闹钟触发后重新计算下一到期时间。

### 2.2 强制频率与负载上限

| 指标 | 默认配置 / 上限 | 必须验证 |
|---|---|---|
| 客户端棋盘快照发送 | **默认 4 次/秒（250ms）**，硬上限 **5 次/秒**，无状态变化不发 | 10 分钟录样本，绝不因 rAF 60 FPS 而发送 60 次/秒 |
| 快照原始消息大小 | 推荐 0.5–1 KiB，**硬限制 4 KiB** | 服务端按字节限制，超限拒绝并统计 |
| 远程棋盘订阅 | **每玩家仅 1 名观察对象** | 6 人房间不能按全员广播棋盘；每名连接收到最多一条远程棋盘流 |
| 全员排行榜 | 最多 **2 次/秒**；得分/状态无变化不发送 | 所有人收到同 revision 的相同排序数据 |
| 连接数量 | 每席位至多 1 条有效 WebSocket；同令牌新连接替换旧连接 | 6 人最多 6 个有效玩家连接 |
| 客户端消息限速 | 快照 5 次/秒，控制消息独立限速；暴发允许极小缓冲，超过丢弃/断开 | 不得因恶意客户端令 DO 无限排队 |
| 队列积压 | 允许丢弃旧棋盘快照，始终只保留最新一份；控制消息不可丢 | 慢客户端不会撑满内存或拖慢其他人 |
| 心跳 | **不做每秒 ping**；仅网络空闲超过约 25 秒时低频保活/健康检测，结合重连判定 | 后台或网络波动不产生频繁服务器唤醒 |
| 写库 | 房间阶段变更、成员变更、终局、必要的定时检查写库；不逐帧写库 | SQLite 写入量不随每秒棋盘帧数线性增长 |

**六人 10 分钟保守预算：** 默认上报 `6×4×600=14,400` 条，硬上限 `6×5×600=18,000` 条；每人恰有一个订阅目标时远程棋盘下行通常同量级（非 `6×5×5×600=90,000` 全互播）。若上行包按 0.5–1 KiB 估算，上行约 7.2–14.4 MiB（默认）或 9–18 MiB（硬上限），不含 WebSocket/TLS 开销、榜单和控制消息。**不保证费用为零**；以 Cloudflare 实际用量统计核验。按照官方文档，DO 免费额度为 100,000 请求/天、13,000 GB-s/天（Workers 另有独立计量），WebSocket 消息依平台规则计费；不能将网络字节和 Workers 请求额度混为一谈。

**性能保护机制：** 按序号去重、丢弃陈旧快照；单连接只推送当前观察对象变化的最新帧；排行榜在可用的入站消息/状态变更时按时间戳合并发布，不为限频添加常驻 setInterval；服务端**不要对每一条棋盘帧重新排序全房间榜单**，只在得分/状态改变时标记 dirty，再以限频批处理；观战目标也只在相关得分或成员状态改变时重新计算（并防抖 ≤500ms，错误目标最长存在 <1 秒）。客户端解码/绘制遵循可见性策略：自己的主棋盘优先，远程小棋盘无新帧不重绘。

### P1：Cloudflare Worker / DO 基础

- [ ] **N08 — Wrangler/DO 骨架与本地模拟**。范围：`worker/wrangler.jsonc`、`worker/src/index.ts`、`worker/src/room.ts`、Worker package；不动原 deploy.yml。执行：配置 SQLite-backed Durable Object migration、显式兼容日期、公开 API 原点及 CORS 白名单；使用 Wrangler 本地模拟。验收：本地 worker 可启动；DO 绑定可实例化；原 GitHub Pages 工作流文件未变。
- [ ] **N09 — 房间码冲突与代际隔离**。范围：`worker/src/room.ts`（必要时抽取 `room-store.ts`）+ 并发测试。执行：房间码由 Worker 使用 `crypto.getRandomValues` 随机取值并重试；每个码映射固定 DO，**同一个码的有效占用/代际更新在该 DO 内原子完成**；定义候选冲突后最多尝试次数和创建失败错误，禁止客户端先检查再提交。验收：用并发 50/100 次混合测试无重复**同时有效**房间码；模拟释放并复用原码后旧 generation/旧凭据无效；码空间耗尽/重试上限返回可控错误。
- [ ] **N10 — 创建房间 HTTP 接口及最低防滥用门槛**。范围：`worker/src/index.ts`、`room.ts` + 测试。执行：`POST /api/rooms` 接收昵称、人数、随机模式、自定义种子和初始等级，签发强随机席位令牌；禁止回显内部摘要；**在正式创建 DO 前实现请求体字节限制、来源校验和有限的创建频率门槛**，复杂规则统一在 N22 加固。验收：所有合法组合通过，非法参数 4xx、超过初始门槛返回 429；6 位码不会因恶意大包无限创建 DO。
- [ ] **N11 — 加入与容量/昵称原子校验**。范围：`worker/src/room.ts` + 测试。执行：`POST /api/rooms/:code/join`，只允许大厅加入；检查总人数、名字大小写冲突、席位身份；多个用户同时最后席位只能成功一人。验收：2～6 人容量逐一测试，满员、错误码和已开赛加入均正确拒绝。
- [ ] **N12 — 席位、房主转移与主动退出**。范围：`worker/src/room.ts` + 测试。执行：服务端保存席位权限、房主标识及加入序号；退出释放席位，房主按存活连接/加入顺序转让；避免旧房主凭据继续操作。验收：房主退出后新房主唯一，最后一人主动离开立刻关闭房间业务状态。
- [ ] **N13 — 无泄漏 WebSocket 认证**。范围：Worker 握手入口及临时票据逻辑 + 测试。执行：席位 token 放会话存储，不用持久 token URL 参数；单次短期握手票据，校验 Origin、过期、重放、generation；每席位仅一条活动连接。验收：错误票据、过期、旧世代、非法来源全拒绝；正常跨域 WSS 成功。
- [ ] **N14 — DO WebSocket Hibernation 接线**。范围：`worker/src/room.ts` + 模拟测试。执行：`acceptWebSocket`、事件回调、附件恢复与热重启重建连接上下文；不得 `ws.accept` 与 Hibernation 混用。验收：DO 休眠/重建后连接身份、房间配置可恢复；无常驻轮询。
- [ ] **N15 — 服务器会话状态机与准备**。范围：`worker/src/room.ts` + 测试。执行：`LOBBY → COUNTDOWN → RUNNING → FINISHED` 及下一局流程；房主更新配置、玩家 ready；**房主更新配置后使已有准备状态失效并要求重新准备**；开始前冻结名单/随机选项。验收：人数不足、未准备、非房主启动均失败；改配置后准备状态重置；开赛后非法加入/改参数失败。
- [ ] **N16 — 统一倒计时与开局种子派生**。范围：`room.ts`、`shared/protocol.ts` + 测试。执行：服务端决定 `startAt`、`deadlineAt`、PRNG 算法版本与每席位 seed，下发一致时间；不逐秒广播倒计时。验收：三模式跨客户端产出约定牌序，临界时刻与提前开始拒绝。
- [ ] **N17 — 600 秒到期闹钟**。范围：`room.ts` + 假时钟测试。执行：只有服务端权威时间可触发超时，DO Alarm 到期独立计算胜负，要求幂等；闹钟由持久化 deadline 重建，不在每个玩家的心跳上轮询。验收：599999ms 不结束，600000ms 结束；浏览器均离线也不延长。
- [ ] **N18 — 淘汰及提前终局裁决**。范围：`room.ts` + 测试。执行：校验成员淘汰/退出事件的身份和比赛状态；**只认当前局 matchId，严格校验已接受的服务端淘汰时间，禁止客户端指定淘汰时间**；最后 1 人立即胜出；0 人同刻出局可并列。验收：2～6 人淘汰序列、重复淘汰事件、已结束事件都幂等。
- [ ] **N19 — 超时获胜和最终名次**。范围：`worker/src/ranking.ts` + 测试。执行：生存者优先、分数→消行、完全并列；已淘汰按淘汰时间处理，胜者独立表示。验收：已死高分不夺冠，并列可被明确表达；排行榜代码绝不与最终名次代码互相复用排序结果。
- [ ] **N20 — 断线宽限与单席位重连**。范围：`room.ts` + 假时钟/重连测试。执行：断线 30 秒可凭原席位重新连接，旧 socket 被替换；超过 30 秒对**该局参赛者**判淘汰，席位数据仍可存续至房间到期/主动离开；**不把 30 秒淘汰误当 30 分钟房间清理**；联网比赛不停表。验收：29.999 秒可恢复、30 秒超限淘汰，刷新不增加一名新玩家。
- [ ] **N21 — 房间空置与到期清理**。范围：`room.ts` + alarm 假时钟测试。执行：全员主动离开立即释放数据；所有 WebSocket 意外断开则记录空置起点并最迟 30 分钟释放；取消/重排当前最近截止 Alarm。验收：无人 29 分 59 秒房间业务记录仍存在（**不意味着超出 30 秒者仍可复活比赛**），30 分钟到期清理业务数据；取消后旧 token 无效；倒计时/比赛截止闹钟不会被空房闹钟覆盖。

### P2：限流、数据传输与观战

- [ ] **N22 — HTTP 防滥用策略加固**。范围：Worker HTTP 入口 + 测试。执行：创建与试码限流/冷却，Origin/CORS 白名单；禁止在 Worker 内无限增长进程级 Map，当按 IP 的分布式限制无法由现有设施保证时明确使用 Cloudflare Rate Limiting Rules 或等效有限状态机制。验收：在本地模拟与可用 Cloudflare 规则环境中高频创建/试码被拒绝，记录**边缘限流规则的配置/依赖**；若免费计划无法支持所需分布式 IP 限流，则在生产开关中禁用公开创建直至替代机制落实；正常好友访问不误拒。
- [ ] **N23 — 棋盘快照紧凑编码**。范围：`src/net/snapshot.ts`、`shared/protocol.ts` + 测试。执行：严格包含棋盘 24×10、活动块、得分、消行、等级、状态和 seq；优先紧凑 JSON，禁止图片/Canvas PNG 传输。验收：正常编码/解码一致，硬大小 ≤4 KiB；异常行数、非法格值立即拒绝。
- [ ] **N24 — 客户端快照限频与去重**。范围：`src/net/publisher.ts` + 测试。执行：节流到默认 250ms，最大 5Hz；无变化不发；连接失效或单机模式不发；慢网只保留最新一帧。验收：10 分钟模拟最多 2400 条/玩家（默认），60 FPS 不造成 36000 条上报。
- [ ] **N25 — 服务端快照校验、限流与背压**。范围：`room.ts` + 负载测试。执行：按席位身份、4KiB **原始字节**、seq、每秒硬上限校验；丢弃陈旧/多余消息，积压时丢旧保新；**服务端仅接受符合已冻结 matchId 的成绩，不信任客户端提供 playerId/status/获胜者**；绝不为每帧写入 SQLite。验收：恶意 100Hz/1MiB/乱序请求不能迫使 CPU/存储无限增长。
- [ ] **N26 — 服务端单目标快照路由**。范围：`room.ts` + 模拟 6 个 socket 测试。执行：建立目标订阅映射，仅向“当前观察该玩家”的连接发送其新快照，切换目标时立即补发目标最后一帧。验收：6 人最大每玩家只收到 1 条目标快照流，转发量近似 O(N)，不得 O(N²)。
- [ ] **N27 — 统一积分排行榜纯函数**。范围：`worker/src/leaderboard.ts` + 测试。执行：全员按得分降序、同分并列名次、消行/加入序稳定显示；死人继续显示，胜者另标记。验收：同一房间所有客户端接收完全同 revision 的榜单，不因自己的名字/观察目标而重排。
- [ ] **N28 — 排行榜 dirty 批处理与发布**。范围：`room.ts` + 假时钟测试。执行：成绩/状态改变标记 dirty，通过事件时间戳门控最高 2Hz；**无待发送变化时不唤醒，避免常驻 500ms 定时器或每次变更调用 Alarm**；对最终结果、淘汰等关键状态允许立即广播；不按每个快照做全员重排。验收：6 人 5Hz 快照压力下榜单最高 2Hz，无不必要写库。
- [ ] **N29 — 自动观战目标纯函数**。范围：`worker/src/watch-target.ts` + 测试。执行：刚好更高者；若自己最高/并列最高则最低者；同分 tie 按批准方案，淘汰者参与；不得选择本人。验收：覆盖两人、六人、全同分、并列最高、淘汰者、高低分轮换 ≥10 组。
- [ ] **N30 — 目标切换与客户端事件**。范围：`room.ts` + 测试。执行：观战目标仅在排行榜 revision/房间状态改变时重新计算，按入站事件合并而非新增定时器，目标应在 **≤1 秒**内稳定；向每个用户单独发送 watch_target；不修改公共排行榜。验收：A、B 各看不同对象时榜单仍逐字段一致，目标切换后的旧快照被丢弃。

## 4. 独立复审必须检查的高风险点

| 风险 | 不可接受的实现 | 必须采用的修正 |
|---|---|---|
| 房间码竞争 | Worker 检查空闲 → 非原子写入 | 按码映射 DO 并在同一 DO 原子登记 generation |
| 时间边界 | 每秒后台定时器自增、客户端说比赛结束 | 服务端 startAt/deadlineAt + DO Alarm 幂等裁决 |
| 重复流量 | 60fps 发送，6 人全互播 | 默认 4Hz，硬上限 5Hz，仅订阅一个对手 |
| CPU/内存膨胀 | 每消息做排序、消息积压无限缓存 | dirty 榜单合并、丢弃旧帧、独立控制消息队列限额 |
| 存储写放大 | 每 250ms 保存 6 人全棋盘至 SQLite | 只保存关键业务状态与最新成绩，棋盘可重发 |
| 空房占费 | 每房间 setInterval/不清 socket | DO Hibernation + Alarm，离房/空置自动释放 |
| 同分处理 | 各客户端自排不同顺序 | 服务端统一榜单 revision，同分名次并列 |
| 胜负和得分混淆 | 高分死者被评为冠军 | 生存胜者独立结算，榜单只按分数 |
| 作弊边界 | 宣称服务端权威物理/绝对防作弊 | 仅休闲好友赛，服务器限流和合法性基本检查 |
| 单机退化 | 把网络逻辑塞进 GameEngine | `game/` 纯逻辑；模式装配隔离，原部署不变 |

## 5. Cloudflare 部署准备与凭据处理

已确认 Cloudflare 连接可用（仅做了身份识别和文档查询，**没有创建或改动任何资源**）。实际实施 N44 时需要：

1. 一个可用的 Cloudflare Account 及 Worker 创建/更新权限，账号关联的 API 访问由已连接的 Cloudflare 工具处理，**无需提供明文 Token**。
2. Worker 名默认 `neon-blocks-room`；须先只读确认同名 Worker 是否已有业务，若被占用则选择不冲突名称，不能覆盖既有资源。
3. 使用 SQLite-backed Durable Object，首次部署要配置 migration tag；确认账号免费计划支持且相关额度仍有效。
