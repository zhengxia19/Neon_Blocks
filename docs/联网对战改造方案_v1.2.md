# 霓虹方块 2～6 人联网对战改造方案 v1.2（已批准）

- **状态**：用户已批准方案；此文件仅为设计文档，具体实施按原子任务清单执行。
- **日期**：2026-10-19
- **源码**：https://github.com/zhengxia19/Neon_Blocks
- **现有网站**：https://zhengxia19.github.io/Neon_Blocks/
- **目标**：在保留 GitHub Pages、Vite、TypeScript、Canvas 2D、单机玩法与核心规则模块的前提下，增加 2～6 人通过六位房间码进行同步竞赛／生存淘汰。第一期**不加入垃圾行攻击**。

## 1. 确认范围、边界与架构

### 1.1 必须交付

1. 玩家在游戏首页选择「单人游戏」或「联网对战」；单人功能和部署保持原样。
2. 房主创建 2～6 人房间，获得唯一的、在有效期间可用的六位数字房间码（100000～999999）。
3. 玩家从各自终端输入房间码和名称加入，无账号注册。
4. 房主选择方块随机模式及初始速度等级；房间未开局前允许修改并同步，开局后锁定。
5. 统一准备、倒计时、服务器确认开局；每局最长 600 秒，剩余一位未淘汰玩家立即结算。
6. 联网游戏必须展示实时积分排行榜（所有参赛玩家），并且只绘制**自己的棋盘 + 一个自动选定的对手棋盘**。
7. 处理离开、掉线、恢复、房主转移、赛后结算和房间空置回收。
8. 在普通 PC 浏览器和移动浏览器上运行；保留中文文案、现有按键和触控操作。

### 1.2 不做（明确排除）

- 垃圾行攻击、文字／语音聊天、登录注册、好友系统、全球积分榜、长期战绩／数据库；
- WebRTC、屏幕截图、视频流、独立 VPS；
- 每帧服务器物理计算、服务端逐按键回放、完整反作弊系统；
- 修改现有 `.github/workflows/deploy.yml` 或替换 GitHub Pages 托管。

### 1.3 技术结构

```text
任意浏览器（GitHub Pages：原站点）
   ├── 单人：原 GameEngine → Canvas，本地运行（无需网络 API）
   └── 联网：原 GameEngine（注入种子及初始等级）
              ├── 本地 Canvas／输入
              ├── WebSocket 客户端（状态上报、事件接收）
              ├── 排行榜 UI
              └── 远程棋盘只读 Canvas（复用原方块绘图）
                           ↕ WSS / HTTPS
Cloudflare Workers（HTTP 接口、认证、速率限制、路由）
                           ↕
Durable Objects（SQLite-backed；每个有效房间码对应一个逻辑房间）
   ├── 房间配置／会话令牌及玩家槽位
   ├── WebSocket Hibernation 连接与转发
   ├── 服务端时钟、排名、结束判定
   └── 闹钟清理／游戏时间上限
```

**部署边界**：原 GitHub Actions 继续只负责前端静态文件。`worker/` 可独立通过 Wrangler／Cloudflare Workers Builds 部署。前端注入的是**公开 API 根地址**，Cloudflare 管理令牌只能保存在部署环境，不允许进入网页构建产物。

## 2. 房间与玩家规则

| 属性 | 规则（本版默认值） |
| --- | --- |
| 房间人数 | 房主选择 2、3、4、5、6 之一；最少两人才能开局；最多 6 人 |
| 房间码 | 6 位数字，100000～999999；有效房间内唯一；显示和复制时不加空格，展示可分组 |
| 玩家名称 | 必填，`^[A-Za-z0-9]{1,16}$`：1～16 个 ASCII 英文字母/数字，不允许空格、标点、中文、控制字符 |
| 重复名称 | 同房间大小写不敏感地拒绝同名；提示重新填写；不同房间可以同名 |
| 玩家身份 | 服务端签发随机不可预测的席位令牌；房间码不能代替令牌；房主权限绑定房主席位 |
| 会话存储 | 会话令牌只保存在本设备会话级存储以支持本标签页刷新重连；不上传到 GitHub、URL、日志 |
| 后加入 | 仅等待大厅可占新席位；开始后关闭新玩家加入，原玩家可凭令牌重连 |
| 房主退出 | 如仍有玩家，按加入顺序转交最早仍在房间的玩家；如无人，立即失效清理 |
| 房间重用 | 一局结束后可以由房主发起下一局，所有玩家重新准备，开始时重新确定种子和比赛计时 |
| 退出 | 主动点击「退出房间」立即释放席位；比赛中视为淘汰；如最后一人明确退出，房间立即失效 |
| 意外断连 | 先标记「连接中断」；允许 30 秒凭原令牌恢复，不立刻判负；超时仍未恢复则淘汰 |
| 无人在线 | 全部 WebSocket 离线时开始 **30 分钟最长空置倒计时**；期间只接受原席位凭令牌恢复，若有效比赛已结束或到期按服务端规则处理；到期逻辑清理 |
| 等待大厅 | 默认未开局可保留；若没有任何活动消息／连接 30 分钟则过期；创建房间未实际连接也按此规则清理 |
| 服务端存储 | 清理时取消相关闹钟、关闭连接、删除房间业务数据，使旧令牌和房间码不可用；不承诺删除 Cloudflare 平台层面的 Durable Object ID |

**码碰撞**：随机生成六位码后，在与码同名的 Durable Object 内原子检查是否有有效业务房间；冲突则换码重试。对象 ID 可长期存在，不代表该码永久占用。需要标识逻辑房间的 `generation`，防止旧连接或旧令牌复用清理后重新分配的相同码。

**安全限制**：创建与试码接口均做按来源限流；错误房间码、满员、比赛开始后加入及非法令牌须给出明确中文提示。禁止信任客户端传入的 `playerId` 来更换自己身份。

## 3. 房主可选择的对局参数

### 3.1 方块随机模式（明确提供三种）

| 选项 | 名称 | 生成规则 | 公平性说明 |
| --- | --- | --- | --- |
| S1（默认） | **系统随机·所有人同序列** | 开局时服务端用安全随机数创建 32 位主种子，所有玩家用同一种子和同一 PRNG；各自的 7-bag 序列相同 | 最适合比较技术与速度 |
| S2 | **系统随机·每人独立序列** | 开局时服务端创建主种子，再根据稳定席位 ID 派生每人的种子；都可以重现，但方块顺序不同 | 运气因素较大，作为休闲模式 |
| S3 | **房主指定种子·所有人同序列** | 房主输入 1～32 位英文字母或数字（大小写敏感），使用固定哈希归一化为 32 位种子，再对全员使用相同 PRNG | 可复盘固定牌序，适合比赛或重复练习 |

- 所有模式继续使用原来的 **7-bag** 规则，禁止直接改为逐块等概率抽签。
- 服务端确定最终 `seed`／算法版本并在开始消息中广播；前端使用固定实现（建议 `mulberry32` 或明确选定的可跨 JS 环境重现 PRNG，最终以金样本测试锁定）。**不能继续使用默认 `Math.random` 运行联网牌序。**
- 相同种子和相同取牌次数产生同一序列；Hold 会影响每位玩家拿取队列的进度，但不能导致 PRNG 与 7-bag 逻辑不确定。
- 房主开局前可更改模式或种子。开局后禁止更改；下一局可以重新选择。
- S3 输入不允许密钥、账号或个人信息性质的字符串，界面只把它当游戏参数。

### 3.2 初始等级 / 下落速度

- 房主选择 **1～10** 级，默认 1 级；所有玩家同一等级。
- 等级对应现有 `src/game/constants.ts` 速度表：1 级 900ms／格，10 级 170ms／格。
- 保留原有「每消除 10 行升级一次」机制。联网等级公式：`level = startLevel + floor(lines / 10)`，10 级以上继续沿用当前 `gravityIntervalMs` 的公式及 60ms 下限。
- 单人公式保持 `level = 1 + floor(lines / 10)`，不得改变。
- 服务端对初始等级做 1～10 整数校验，房主未开局前修改立即同步到大厅。
- **不额外增加固定速度模式**，避免与原单机升级机制发生需求分叉。

## 4. 比赛流程、时间与胜负

```text
LOBBY（等待／可修改参数）
  → COUNTDOWN（3 秒倒计时，服务器下发开始时间）
  → RUNNING（所有玩家本地同步竞赛）
  → FINISHED（只剩一个存活玩家，或达到服务器开始后的 600 秒）
  → LOBBY（房主发起下一局，所有人重新准备）或 CLOSED
```

1. **开始条件**：实际在场且都完成准备的参赛席位不少于 2 人、不超过设定容量；由房主点击「开始」，服务器核对后锁定参赛名单和比赛参数。
2. **倒计时**：服务器广播同一 `startAt` 绝对时间；各客户端以服务器时钟偏差校正显示 3、2、1；无法在确认 `startAt` 后开始的客户端视为断连恢复，不能单独延迟比赛。
3. **时间上限**：比赛计时只以服务器 `startedAt` 与 `deadlineAt=startedAt+600000` 毫秒为准；浏览器切换标签页不能停止计时，服务器到期闹钟必须能独立结算。
4. **淘汰事件**：本地引擎 `gameover` 上报；服务端验证其当前席位与状态、记录服务器接收时间并广播；主动退出或超过断线宽限期也视为淘汰。
5. **提前结束**：参赛玩家中恰剩一名未淘汰时，服务器**立即宣布其为获胜者**并结束本局，无须等满 10 分钟。
6. **超时结束**：如果 600 秒到达时仍有多名存活者，先在存活者中按`分数降序`、再按`消行数降序`排序确定名次；分数和消行数都相同则并列第一，明确展示「并列获胜」而不暗中按玩家 ID 判胜负。已淘汰者不能赢得超时局。
7. **极端同时淘汰**：如果在同一个结算批次出现零存活者，则根据最后淘汰时刻（越晚越优先）与分数、消行数判定；完全同条件允许并列，不凭网络到包顺序随意分胜负。
8. **其他名次**：已淘汰玩家最终排名按存活时间从长到短排列；同一时刻淘汰的按分数、消行数排列。比赛进行中的「积分榜名次」与比赛结束后的「生存赛最终名次」必须清晰区分。
9. **暂停**：联网对局禁用个人暂停；单人模式的暂停仍可使用。打开设置不应让联网引擎暂停服务端时间；玩家应能退出但不能停止比赛倒计时。
10. **重新开始**：联网对局期间不允许任意本地重开；由房主在本局结束后控制下一局。

> 首期采用客户端执行游戏物理、服务器负责房间／胜负／时间与校验的设计。服务器不会逐次重算所有方块，因此**无法完全阻止改写客户端伪造成绩**；定位为好友休闲对战。基础防护包括分数单调性、字段范围、移动速度异常监测、身份和消息频率限制，不能宣传为严格反作弊。

## 5. 全员统一的实时得分排行榜（与双棋盘选人完全独立）

**强制区分两种 UI 数据：** `roomLeaderboard` 是服务端按分数排序后广播的全房间共享数据，所有客户端相同；`observedPlayerId` 是按当前玩家分数单独计算的观战目标，各客户端可以不同。禁止使用 `observedPlayerId` 或本人位置重排榜单。

- 对战界面固定有 2～6 人全员积分榜，包含：**积分名次、玩家名称、当前分数、消除行数、存活／离线／淘汰状态**；标记「我」及房主。
- **排行榜所有玩家完全一致**：服务器生成**一份房间统一榜单**，同时广播给每个人。所有本局参赛者（含已淘汰者）一律先按`分数降序`排列；分数相同者显示**并列得分名次**，仅用`消行数降序 → 加入顺序升序`稳定显示顺序（不影响并列名次）。玩家本人仅作视觉高亮，不改变榜单顺序。
- 服务端接收客户端成绩后成为排行榜消息的唯一发布者。客户端不能自行定义他人名次。
- 状态上报上限 5 次／秒／玩家（200ms）；排行榜最多广播 2 次／秒，状态无变化时不发送冗余更新；倒计时由本机根据服务器时间推算，每秒更新数字，无须每秒网络推送。
- 断线玩家在宽限期内显示「连接中断」，超时显示「已淘汰」。已经死亡的玩家继续留在排行榜，分数固定。
- **结束后排行榜仍维持得分降序**，不切换排序逻辑；在排行榜上方或结果面板另行突出显示**生存赛胜者和最终淘汰结果**。因此「得分第一」不一定是「本局获胜者」，两者必须明确分离。

## 6. 严格限定双棋盘与对手自动选择（不影响第 5 节统一排行榜）

### 6.1 布局

- 任意人数始终只有两张比赛棋盘：**自己的棋盘**与**选中对手的棋盘**。
- 桌面：本人棋盘宽 300px 级别（保留原体验）；对手棋盘约为本人的 55%～70%，旁边显示全员排行榜；不绘制第 3～6 张棋盘。
- 手机：本人棋盘与触控按钮始终占优先空间；选中对手棋盘缩略显示在上方／右侧或可折叠区，不能遮挡操作按钮；排行榜允许折叠但必须可即时查看全部玩家。
- 对手棋盘通过复制状态快照并复用 Canvas 棋盘绘图来展示，**不截屏、不视频、不重新运行别人的 GameEngine**。

### 6.2 自动选择算法（精确定义）

**候选集合**：本局全部参赛者，排除自己；**包括已经被淘汰的玩家**（其棋盘冻结，标注「已淘汰」），从而严格满足「房间内得分刚好比自己高」的字面规则。

1. 令本人得分为 `myScore`，选出所有 `score > myScore` 的其他玩家。
2. 若集合非空，选择其中 `score` 最低者，即比自己**高得最少**的人；同分按消行数降序、然后加入顺序升序稳定选一个。
3. 若没有更高得分者（本人并列或独占最高），选择所有其他玩家中`score`最低者；最低分并列则按消行数升序、加入顺序升序稳定选一个。
4. 得分或参赛者状态变化后服务端**仅针对当前观看者**重新确定观察目标并通知该客户端；同一房间内不同玩家可能观看不同对手，**但收到的积分排行榜数据及排序完全相同**；为防反复切换，目标改变时允许最多 500ms UI 防抖，但不得在 >1 秒内停留在错误目标。
5. 对手棋盘显示该玩家昵称、分数、消行数、存活状态；当该人淘汰仍符合规则时显示冻结的最后棋盘。联网断开则显示「同步中断」而不是清空或用假画面。

**例子**：A=900、B=1400、C=300、D=900、E=2000、F=500：A 观看 B（1400）；E 观看 C（300）；D 与 A 的目标都按上述严格高分筛选，而不是用排行榜的行位置替代分数比较。六人同分时，无更高分者，按最低分并列的稳定规则选择其他玩家。

> 如果今后希望「只观看未淘汰对手」，那属于另一个业务规则，会改变现在明确要求的纯得分选择方式，本版不擅自添加这一例外。

## 7. 网络协议与性能约束

### 7.1 HTTP 入口（仅示意，开发时锁定契约）

- `POST /api/rooms`：房主创建房间，提交名称、容量、随机模式、可选种子、初始等级；返回房间码、席位令牌、服务器创建时间。
- `POST /api/rooms/:code/join`：加入房间并获得独立席位令牌；服务器校验满员／姓名冲突／游戏是否已开始。
- `GET /api/health`：健康检查（仅版本／状态，不暴露房间或玩家信息）。
- `GET /api/rooms/:code/ws`：WebSocket Upgrade，凭席位令牌认证；浏览器需遵循可实现的 WebSocket 鉴权方式，例如连接前签发短期一次性握手票据，**不把长期席位令牌拼进 URL**。

### 7.2 WebSocket 消息（协议字段要固定版本）

- 客户端 → 服务器：`ready`、`start`、`settings_update`、`snapshot`、`gameover`、`leave`、`ping`。
- 服务器 → 客户端：`room_state`、`player_joined`、`player_left`、`countdown`、`match_start`、`scoreboard`、`watch_target`、`remote_snapshot`、`match_end`、`error`、`pong`。
- 公共字段：`v`（协议版本）、`type`、`seq`／`revision`、服务端时间戳；消息允许字段必须进行白名单校验。
- `snapshot` 包含 24×10 棋盘（建议每行 10 个枚举字符，包含隐藏区）、活动块（类型／旋转／坐标）、分数、消行数、当前等级、运行状态及递增序号。所有字段均有尺寸、类型、取值边界，最大消息大小建议 ≤4KB。
- 服务端只向每个玩家发送其当前指定目标的远程棋盘快照，**不要对全房间广播每位玩家的完整棋盘**。排行榜仍全员广播。
- 网络消息采用 HTTPS／WSS；后端校验 Origin 来源、速率、房间席位权限；CORS 只允许正式 GitHub Pages 来源（本地开发白名单仅测试使用）。

### 7.3 网络稳定性

- 快照上报至多 5 次／秒；无变化不发；服务端按 `seq` 丢弃乱序旧消息。
- 远程棋盘延迟目标：在普通宽带连接下，理想情况平均视觉更新延迟 <500ms；验收以模拟网络迟延测试与真实浏览器为准，不作端到端保证。
- 断开后本地比赛如何处理：**不暂停服务端比赛时间**。本地可以显示遮罩并停止输入，恢复后根据服务端当前房间状态重建显示；超过 30 秒宽限淘汰。
- 如 Durable Object 因空闲休眠被重建，通过持久化房间元数据、Socket 附件和客户端重发快照恢复一致状态；不能只依赖对象内存保存房主／房间配置。
- 服务器保留 10 分钟比赛的超时闹钟，空房间保留最长 30 分钟回收闹钟；单个 Durable Object 的闹钟调度应选最早截止事件，避免相互覆盖。

### 7.4 初期容量估计

六名玩家，每人 5 次／秒，10 分钟：`6×5×600=18000` 条上报消息；因每人**只订阅一个对手棋盘**，对应棋盘转发通常也是约 18000 条／局（非六人全互播的 90000 条）。再加少量积分榜、房间和心跳消息，仍属于轻量实时应用。上行报文按 0.5～1KB／条估算，约 9～18MB／局（仅状态上行）；实际用量以测试计量为准。

## 10. Cloudflare 部署前需要用户提供／完成什么？

### 10.1 最小必要信息

1. **Cloudflare Account ID**（账号标识，非 API 密钥）。
2. **目标 Workers 名称**：建议 `neon-blocks-room`；确认不存在同名冲突或愿意新建。
3. **对外 API 地址选择**：首版推荐 Cloudflare 免费 `*.workers.dev`，无需提供自有域名或 DNS Zone ID；将来选择自有域名再提供区域信息。
4. **部署授权方式**：用户在受控的本机终端配置 `CLOUDFLARE_API_TOKEN`／`CLOUDFLARE_ACCOUNT_ID`，或通过可执行 Cloudflare 部署的已连接工作环境授权。不要将明文 token 写入仓库、任务文件、前端环境变量或聊天。
5. **Token 权限**：当前 Cloudflare 新角色体系下，**新建 Worker** 需要 Workers 产品范围 `Admin`；**更新已存在 Worker** 只需该 Worker 或 Workers 产品范围 `Editor`。Durable Objects 本身依赖 Worker 权限，无须额外授予独立 DO 角色。若将来绑定自有域名，还需要相应 Zone 的 Workers Routes Write 权限。
6. **Workers Free 功能确认**：Cloudflare 账号可使用 Workers 与 SQLite-backed Durable Objects，并允许启用 Workers 的 `workers.dev` 子域名。

### 10.2 配置与环境区分

- Cloudflare API Token **只用于部署管理**，浏览器访问房间不需要 Cloudflare 管理 Token。
- 前端公开变量仅包含 API 地址，例如 `VITE_GAME_API_BASE=https://neon-blocks-room.<subdomain>.workers.dev`；不能把 Cloudflare 管理 Token 放进以 `VITE_` 开头的变量。
- 后端 CORS／WebSocket Origin 白名单：正式站点 `https://zhengxia19.github.io`（Origin 不包含 URL 路径，路径另行验证）。
- Worker 与 DO 在同一后端项目中部署，配置一个 SQLite-backed DO 绑定；按当前 Wrangler 规范使用 migrations／class 声明。
- **当前会话具有 GitHub 仓库操作能力，但未发现可直接操作 Cloudflare 账号的已连接工具**。即使用户已有 Cloudflare API Token，也不意味着此会话已获 Cloudflare 操作能力；实施时需要可用的授权部署通道，或在用户本机执行 Wrangler。
- 现阶段**不请求**账号信息、Token，也**不执行部署**；须先确认此设计方案。

### 10.3 免费额度判断

2026-10-19 核对官方文档：Workers Free 支持 SQLite-backed Durable Objects；免费计划 Durable Objects 请求约 100,000／天、时长 13,000 GB-s／天，存储配额 5GB；WebSocket Hibernation 推荐用于减少空闲时长计费。计费规则和实际表现会调整，实际容量以官方控制台计量为准。首批 2～6 人私密房间预计可以在免费额度内运行，仍需压力与长期在线测试。

## 12. 复审结论与批准闸门

- **架构可行性：高**。现有 `GameEngine` 的可注入 RNG、Canvas 渲染和独立静态部署天然利于加网络协调层。
- **初期开发复杂度：中等**。真正困难处在 6 人状态同步、比赛结算、身份重连、端侧失焦以及 Durable Object 生命周期，而非六位码或第二块 Canvas。
- **性能／免费额度：初步高置信度可行**，以真实联机压力测试确认。
- **公平性：休闲级**。客户端可提交分数，未实施权威服务端物理验证；切勿将其视作严格竞技防作弊方案。
