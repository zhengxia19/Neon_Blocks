# 霓虹方块联网对战实施题词（DeepSeek Harness /goal 模式）

> 在 DeepSeek Harness 的 **Work 模式**中，将下面正文作为**一个完整的 /goal 目标**提交；不要把 N01～N44 全部拆成 44 个并行队列任务。插件并发设置为 1，同一个仓库只允许运行一个写入目标。

## 总目标

在本地工作区完成 Neon_Blocks 的 2～6 人联网对战改造，按批准的方案和已复审的原子清单 **N01 → N44 串行实施，逐项验证，阶段复审，持续保存进度**。保留现有单人模式和 GitHub Pages 发布工作流，联机服务器采用 Cloudflare Workers + SQLite-backed Durable Objects + WebSocket Hibernation。

目标完成的判据：所有必要任务真实验收通过；2～6 个终端可通过六位房间码加入、按房主设置的种子模式及初始速度同步竞赛；最多 10 分钟并在仅剩一位存活玩家时立即结算；全员统一按分数排列的排行榜；每人固定两幅棋盘且第二幅按个人得分选择；服务器及网络限流、断线、房间清理均通过验证；原单机回归通过；文档及证据完备。**Cloudflare 生产部署需明确确认后执行，不得把未经部署的工作宣称为已上线。**

## 第一步：本地仓库准备（必须先完成）

1. 先确认执行终端系统、当前工作目录、是否为 Git 仓库、Git/Node/npm 版本、是否已有同名工作区；不询问用户已能自动检测的信息。所有源码修改必须在**本地仓库**完成，不能以远程 GitHub 网页作为工作目录。
2. 若当前目录已是 `zhengxia19/Neon_Blocks` 的本地克隆，验证 `git remote -v` 与 `git status --short`。工作树干净且无未推送提交时可 `git fetch origin` 并按正常快进方式更新；存在未提交修改、未推送提交或分支分叉时**保护已有工作并报告阻塞**，不可强制重置、覆盖或删除。
3. 若尚无本地克隆，在工作区内一个清晰、可写的位置执行 `git clone https://github.com/zhengxia19/Neon_Blocks.git`，然后 `cd Neon_Blocks`。如目标文件夹已存在，先检查它而不是直接覆盖。必须验证 `origin` 与目标仓库一致、分支正确。
4. 运行 `npm ci`、`npm run typecheck`、`npm run test`、`npm run build` 获取基线；Playwright 环境可用时执行既有端到端检查，浏览器未安装需记录并在合适阶段补齐，不虚报通过。
5. 阅读本仓库的 `AGENTS.md`（若存在）、`docs/联网对战改造方案_v1.2.md` 和 `docs/联网对战原子任务清单_v1.1.md`，并检查已完成进度与源代码，确定第一个未验收任务。不仅凭日志中“已完成”的文字跳过任务。

## Goal 模式运行方式（不能只执行 N01 就结束）

1. 将整个 N01～N44 视为**单个长期目标**，内部一次推进一个原子任务；一个任务通过验收后**自动继续**下一个，不需要用户每轮重新发送提示。不要并行修改同一仓库。
2. 每个 Nxx 严格遵守清单所列前置依赖、输入文件、最小改动范围、验收条件和阶段闸门；未通过验证不得标为完成、不得跳任务。
3. 控制 128K 上下文：每次只读取当前任务、对应方案章节和直接关联源码；输入建议 12K～25K tokens、上限建议约 40K；优先更改 1～2 个业务文件，最多 3 个，任务过大拆成 Nxx-a / Nxx-b 且逐步验收。不要把所有测试输出和历史日志放进一次模型上下文。
4. 每个任务记录：任务编号、前置条件、实际改动文件、真实命令与退出码、测试证据、独立复审结论、风险、commit SHA；持久化至 `docs/execution-log.md` 或专用进度文件。仅在证据充分时标记已验收。每个阶段运行必要的回归和独立复审，不重复无意义的全量测试。
5. 运行中断、上下文压缩或工作区重启后，以**本地 Git 状态 + 持久化进度 + 真实测试结果**恢复，不重新执行已验证任务，不重复提交或部署。与 `dsh-goal-queue` 配合时，由队列在**原 Session**执行官方 `/goal resume`；不得因为会话空闲就自动重投同一个 Goal。
6. 提交策略：完成并验收当前任务后做范围明确的 Git commit；正常工作不必每个原子任务都推送公网，原则上通过阶段复审后推送到已授权分支。冲突、鉴权错误、保护分支限制不得强推。
7. 每次输出简短进度摘要，完成后持续推进。遇到缺少权限、方案矛盾、不可逆操作、生产部署或安全风险时，**停在阻塞点、明确列出需要的授权或决策**，不要凭空假定成功。

## 功能与资源红线

- 前端和游戏引擎独立本地运行；服务器仅负责房间码与席位、开始/结束结算、低频榜单、单目标棋盘转发和清理。
- 房主可选择方块随机模式和开局等级；同种子模式必须可复现，且不允许不同玩家自行篡改房间设置。
- 全房间统一、只按得分排序的排行榜，与每位玩家自己选择的一名对手棋盘严格分离。
- 每位玩家快照默认最多 4 次/秒、服务端硬限 5 次/秒；单消息最多 4KiB；排行榜最多 2 次/秒；每名用户只收**一名**其他玩家的棋盘。没有状态变化不发送。禁止全员全量广播、逐帧持久化以及持久在线轮询。
- 服务端必须执行身份认证、长度/频率校验、比赛截止判定；掉线重连与 30 分钟空房清理均须可测试。不能用客户端自行上报的胜者标记直接宣布冠军。
- 禁止泄露或提交 Cloudflare API Token、会话凭据、密钥或隐私数据。保留 `.github/workflows/deploy.yml`，不修改现有 GitHub Pages 架构。
- Worker / Durable Object 开发或预发部署应先确认账号、资源名、绑定及权限；**生产云端部署、删除或其他不可逆变更必须先取得明确授权**。

现在请从**本地工作区检查与必要时克隆仓库**开始，然后按 N01～N44 连续推进。只在必要的真实阻塞或需要授权的节点暂停目标；完成时给出阶段验收摘要、测试结果、提交记录、未决风险和部署状态。
